# CRM Service — End-to-End Audit & Recommendations

- **Date:** 2026-06-07
- **Scope:** Full vertical slice of the **core CRM** — database & data model, backend
  services/handlers/repos, API contract, and frontend UI — across **leads,
  contacts, deals, follow-ups, projects, inquiries**, and their links to
  notifications, reminders, billing, and the calendar.
- **Out of scope:** the **dealer / partner program** (`dealer_*`, `sub_dealer_*`,
  migrations `026/095/106/116`, `features/dealer/*`, `admin/dealers`) — a separate
  B2B bounded context that deserves its own audit. The already-audited calendar
  links in via `events.contact_id`/`deal_id` (see `calendar-audit-2026-06-07.md`).
- **Type:** Read-only documentation audit (no live boot). Findings cite `file:line`.
  Backend/frontend findings were gathered by parallel sub-audits and the
  high-severity items were re-verified directly.

---

## 1. Executive Summary

The CRM has a **broad, well-indexed schema and a create-and-read UI sitting on top
of a backend that never closes the loop**. The data model anticipates a full
funnel — `leads → contacts → deals → projects`, plus `follow_ups` — but the
**core CRM workflow is absent**: leads never convert, deal stage changes have no
side effects, nothing is editable or deletable from the UI, and reminders/follow-ups
never fire.

Four themes dominate every layer:

1. **The funnel is a dead end.** `leads.converted_contact_id` and a `won` stage
   exist, but **no code converts a lead into a contact/deal** (LEAD-1). Deal
   stage changes notify no one and write no activity (DEAL-2). The CRM records
   state but drives no process.
2. **Read + create only.** No CRUD entity has a **DELETE** at any layer, and the UI
   exposes **no edit** for contacts, deals, leads, or projects despite the backend
   having `Update`/`Merge` endpoints (FE-1). The product can capture data it can
   never correct or remove.
3. **Same DB integrity & isolation gaps as the calendar.** Contact/deal/user FKs
   have **no `ON DELETE`** (deleting a contact with deals errors out, D1); RLS uses
   the legacy `app.workspace_id` variable and lacks `FORCE` (D2/D3); plus a real
   JSONB/string type mismatch on `contacts.address` (D4).
4. **Promise vs. reality.** The schema, marketing (`/solutions/crm-contracts`:
   pipeline, follow-up, contracts), and dashboard cards all imply automation and a
   document workbench that are stubs or "planned for M27/M28."

As with the calendar, the platform **already owns** the missing infrastructure
(notification dispatcher with a `bookings` category, cron scheduler, webhooks,
email senders) — the gap is integration, not greenfield.

## 2. Database & Data Model

Tables (migration `021_create_m4_crm_tables.up.sql`, enhanced `073`): **`leads`,
`contacts`, `deals`, `follow_ups`**. (`180_face_identity_contacts` adds a separate
face-identity link.) All four have workspace-scoped RLS and reasonable indexes
(`idx_*_workspace_*`, GIN on `contacts.tags`, partial index on pending follow-ups).

### D1 — Missing `ON DELETE` on key FKs *(High — integrity)*
- `deals.contact_id UUID NOT NULL REFERENCES contacts(id)` (`021:84`) — **no
  `ON DELETE`** → `NO ACTION`. Deleting a contact that has any deal **fails**.
- `leads.converted_contact_id … REFERENCES contacts(id)` (`021:76`) — no `ON DELETE`.
- `follow_ups.{lead_id,contact_id,deal_id}` (`021:113-115`) — no `ON DELETE` → a
  follow-up pins its lead/contact/deal against deletion.
- `contacts.user_id`, `leads.assigned_to`, `follow_ups.assigned_to REFERENCES
  users(id)` (`021:40,14,116`) — no `ON DELETE` → **deleting a user errors** if they
  own/are-assigned CRM rows.

This is the same class as the calendar's D1. Combined with **FE-1** (no delete UI),
the system both forbids deletes structurally and offers no UI for them. Decide the
intent per FK (`SET NULL` for assignee/optional links; `RESTRICT`/soft-delete for
`deals.contact_id`) and apply consistently.

### D4 — `contacts.address` JSONB vs. `*string` *(High — bug)*
`contacts.address` is `JSONB` (`021:46`, never altered) but the repo declares
`Address *string` and binds it directly to the column (`contact_repo.go:23,71,138`).
A plain address string (e.g. `123 Main St`) is **invalid JSON**, so any contact
create/update carrying an address fails the JSONB cast → opaque `500`. Either change
the column to `TEXT` (new migration) or marshal the field to JSON. *(Today it likely
"works" only because the UI never writes `address`.)*

### D2 / D3 — RLS variable drift + no `FORCE` *(Medium)*
All four policies key on `current_setting('app.workspace_id', …)` (`021:34,65,107,
137`) — the legacy variable, while newer tables use `app.current_workspace_id`
(works only because middleware sets both, `db_context.go:32-33`). None declare
`FORCE ROW LEVEL SECURITY`, so the table-owner connection bypasses isolation.
Standardize the variable and add `FORCE` (matches the calendar D2/D3 recommendation
— do them in one migration).

### CON-2 — No uniqueness / dedup *(Medium)*
`contacts` has only a **plain** index on `(workspace_id, email)` (`021:57`), no
unique constraint, and neither `Create` nor CSV import upserts. A CRM that ships a
`Merge` feature but allows unlimited duplicate ingest is backwards. Add a partial
unique index (where email is non-null) and upsert-on-import.

### Reminder/follow-up infrastructure exists but is inert
`follow_ups` has `due_at` + a partial index `WHERE status='pending'` (`021:118,129`)
and `leads.follow_up_date` was added "for reminder tracking" (`073:48-50`), but
**no scheduler job sweeps either** (the cron registry runs only
`monthly-payout-calculation`, `cmd/api/main.go:2799`). Follow-ups never alert — same
root gap as calendar reminders (X1).

## 3. Backend

Files: `contact_handler.go`, `contact_import_handler.go`, `deal_handler.go`,
`lead_handler.go`, `lead_embed_handler.go`, repos `contact_repo.go`/`deal_repo.go`/
`lead_repo.go`, `service/contact_import.go`; routes `routes_m4.go:59-106`.

### Funnel & process gaps *(High)*
- **LEAD-1 — No conversion.** `Lead.ConvertedContactID` and a `won` stage exist, but
  no handler/repo creates a contact or deal from a lead. `UpdateStage`
  (`lead_handler.go:127`) only writes a string. The funnel's central transition is
  unimplemented.
- **DEAL-2 — Stage change is a no-op beyond persistence.** `Update` fires no
  notification (the deals handler holds no dispatcher, `deal_handler.go:14-21`), no
  activity, no webhook, no email. `confirmed`/`completed`/`cancelled` are invisible.
  Contrast with leads, which *do* dispatch on capture (`lead_handler.go:54`).
- **DEAL-1 — Non-transactional fan-out.** Deal insert (`deal_handler.go:57`) and
  `projectRepo.CreateFromDeal` (`:65`) are two independent `Exec`s; a failure after
  the deal insert returns 500 and the retry **duplicates the deal** (no idempotency;
  the project insert is `ON CONFLICT DO NOTHING` but the deal is not). Wrap in one tx.

### Correctness & validation *(Medium)*
- **Silent writes (CON-4/DEAL-3/LEAD-3):** `Update`/`UpdateStage` use `Exec` and
  never inspect `RowsAffected` (`contact_repo.go:128`, `deal_repo.go:145`,
  `lead_repo.go:147,162`) → HTTP 200 echoing the body on a nonexistent/cross-tenant
  id. The client believes a write succeeded that did nothing.
- **Validation (CON-3/LEAD-4):** handlers default a couple of fields but don't check
  `name` (NOT NULL), email format, or enum membership for `contact_type`/`stage`/
  `source` on the authed paths → DB CHECK/NOT-NULL failures surface as `500`. (The
  CSV import path *does* whitelist `contact_type`, `contact_import.go:93` — apply the
  same everywhere.)
- **Full-overwrite PUT (CON-5):** `Update` writes every column from the body
  (`contact_repo.go:133`), so a partial PUT **nulls** unspecified fields (phone,
  tags, notes). No PATCH/merge-with-existing.
- **Info leak (CC-5):** `DealHandler.Create` echoes the raw DB error to the client
  (`deal_handler.go:61,66`); `ImportCSV` echoes `err.Error()`
  (`contact_import_handler.go:46`).

### Public capture hardening *(High)*
- **LEAD-2:** `POST /api/v1/public/leads/{workspaceId}` (`lead_embed_handler.go:32`,
  registered at `main.go:3214`) sets `Access-Control-Allow-Origin: *` and **appears
  to have no rate limiter** (the global/credential/MFA limiters don't wrap it). It
  decodes the **entire** `repository.Lead` (`:48`), so a caller can set
  `assigned_to`, `budget_paisa`, `converted_contact_id`, etc. (only `stage` is
  forced and `name` checked), and each call fires an owner notification/email
  (`:70`). This is an email-amplification + data-poisoning + DoS surface. Add: a
  rate limiter, an HMAC/CAPTCHA embed token, a strict allow-list DTO (name/phone/
  email/event_type/event_date/source only), email-format + length caps, and escape
  `name` in the notification body. **Re-verify the route's middleware chain before
  prioritizing.**

### Other *(Low/Medium)*
- **CC-2:** no activity/audit/soft-delete writes anywhere → `/contacts/{id}/timeline`
  (`routes_m4.go:77`) has no CRM-generated events; merge hard-deletes the source
  (`contact_repo.go:202`) irrecoverably.
- **CC-3:** repos implement `Cursor`/limit≤100 but every handler hardcodes limit 50
  and ignores page params (`contact_handler.go:53`, `deal_handler.go:83`,
  `lead_handler.go:74`) → workspaces with >50 rows can't fetch the rest.
- **CC-7:** CSV import is synchronous, row-by-row, single-connection, no transaction
  (`contact_import.go:47-115`) — partial imports on mid-file failure, no batching.
- **DEAL-5:** `CreateFromDeal` copies deal state into `studio_projects` once; later
  deal edits don't back-sync (`deal_handler.go:111`).
- **Unrouted capability:** `DealRepo.UpdateStage` (`deal_repo.go:158`) and
  `LeadRepo.AssignTo` (`lead_repo.go:169`) exist but are never wired to routes.

## 4. API Contract

### A1 — CRM undocumented in OpenAPI *(Medium)*
`docs/api/openapi.yaml` contains **zero** `/crm`, `/contacts`, `/deals`, `/leads`
paths (`grep` → 0). Like the calendar, the entire CRM surface lives only in code
(`routes_m4.go:59-106`), so it is undocumented for integrators and unguarded by the
`openapi` CI gate.

### Surface summary
Present: contacts (create/list/get/update/merge/import + profile/timeline), deals
(create/list/get/update + follow-ups create/list/complete), leads
(create/list/get/update/stage + public submit), projects (create/list/get/update +
booking/invoice/contract/gallery sub-creates). **Missing across the board:** any
**DELETE**, deal stage PATCH (exists in repo, unrouted), lead assign (unrouted),
real pagination params, and a documented error contract (`400` vs `500`).

## 5. Frontend

Pages under `app/(dashboard)/crm/*`, components `components/crm/*`, client
`lib/api/crm.ts`, taxonomy `lib/crm-taxonomy.ts`.

### FE-1 — Read + create only *(High)*
`crm.ts` wires create + list (+ a few gets) but **no edit/delete** for any entity:
deals are **read-only in the client** (`listDeals` only, `crm.ts:341`); contacts,
leads, and projects have no `updateX`/`deleteX` helper. Backend `Update`/`Merge`
(`routes_m4.go:63,72,73,85,93`) are never called, and **DELETE doesn't exist at any
layer**. Contact detail (`contacts/[id]/page.tsx`) and project detail
(`projects/[id]/page.tsx`) are fully read-only; rows only navigate.

### FE-2 — Core interactions missing *(Medium)*
- Inquiry **kanban can't change stage** — `updateLeadStage` exists (`crm.ts:116`) but
  is never called from `inquiry-pipeline.tsx`; the board is display-only, defeating
  its purpose.
- `/crm/projects` is titled "Project Board" but is a **flat grid with no columns,
  no drag, no status change**, and **no search/filter/pagination** (unlike contacts,
  which uses `useDataTable`).

### FE-3 — Stubs & dead-end navigation *(Medium)*
- `/crm/documents` is a static **"planned for M27"** placeholder
  (`documents/page.tsx:27`) — yet project detail/overview "Create Contract" links
  point users straight to it (`projects/[id]/page.tsx:184`).
- `/crm/deals`, `/crm/price-book`, `/crm/reports`, `/crm/billing` are one-line
  `redirect()` shims to other surfaces.
- Overview cards include hardcoded stubs: "Pending contracts = 0"
  (`crm/page.tsx:244`), "Price book = Open" (`:274`); the "Follow-up queue" card
  actually renders open leads, not follow-ups (`:325`).
- Contact detail synthesizes pseudo-projects from deals with invented
  `contract_status`/`balance_due` when projects are empty
  (`contacts/[id]/page.tsx:136-155`) — display-only fabricated data.

### FE-4 — Auth/design nits *(Low)*
Several helpers use raw `fetch` + manual token instead of the refreshing `authFetch`
(`createLead`, `listDeals`, `getClientProfile`, `getProject`, inquiry create) → "token
expired" instead of refresh. Marketplace panel filters the **full** inquiry list
client-side by `to_user_id` (`marketplace-inquiries-panel.tsx:64`) — pulls other
users' rows to the browser. Raw `<button>` + literal `✕`/`✓` glyphs and ad-hoc `₹`
formatting violate the GlassIconButton/icon-registry and token laws in a few places.

*(No N+1 per-row fetch loops found — list pages use single calls; overview/projects
batch with `Promise.all`/`allSettled`, consistent with the perf hot-path rules.)*

## 6. Cross-Cutting: Promise vs. Reality & Integration

- **Marketing** (`solutions/crm-contracts/page.tsx`) leans on "pipeline",
  "follow-up", and "contracts" — the pipeline can't move stages from the UI,
  follow-ups never alert, and the contracts workbench is an M27 placeholder.
- **Notification integration is one-sided:** only lead capture dispatches
  (`lead_handler.go:54`); contacts and **deals hold no dispatcher** and emit nothing
  on the transitions that matter (stage → confirmed/completed). The
  `NotificationDeliveryService` + `bookings` category already exist.
- **No webhooks** for CRM events despite the webhook subsystem (migration `042`).
- **Calendar coupling:** `events.contact_id`/`deal_id` join CRM↔calendar, but the
  calendar's own D1 FK bug means deleting a CRM contact with events also errors (see
  `calendar-audit-2026-06-07.md`).

## 7. Prioritized End-to-End Roadmap

Dependency-ordered, independently-shippable, flag-gated slices (one unit per PR,
schema→service→API→frontend→flag-on), per repo law.

**P0 — Correctness & safety (small, first):**
1. **D1** Migration: add consistent `ON DELETE` (`SET NULL` for assignee/optional
   FKs; decide policy for `deals.contact_id`) across CRM FKs — pair with calendar D1.
2. **D4** Fix `contacts.address` (column → `TEXT`, or marshal to JSON).
3. **D2/D3** Standardize RLS variable + add `FORCE ROW LEVEL SECURITY` (one migration
   with calendar).
4. **CON-4/DEAL-3/LEAD-3** Check `RowsAffected` → return `404` on no-op writes.
5. **CON-3/LEAD-4 / A2** Handler validation → `400`; stop echoing raw DB errors.
6. **LEAD-2** Harden public capture: rate limit + embed token + strict DTO + escape.
7. **DEAL-1** Wrap deal+project create in one transaction.

**P1 — Close the funnel (the headline gap):**
8. **LEAD-1** Implement lead → contact → deal conversion (transactional; set
   `converted_contact_id`; create activity).
9. **DEAL-2 / CC-2** Deal stage-change side effects: notification (existing
   dispatcher) + activity/timeline write + webhook.
10. **X1** Reminder sweep job for `follow_ups.due_at` / `leads.follow_up_date` →
    notification service (indexed, `FOR UPDATE SKIP LOCKED`) — shares the calendar
    reminder engine.
11. **FE-1** Wire edit + delete UI for contacts/deals/leads/projects (+ client
    helpers); add the missing DELETE endpoints.

**P2 — Interactions, docs, dedup:**
12. **FE-2** Lead kanban stage change (drag → `updateLeadStage`); real project board
    + search/filter/pagination; wire project sub-resource create endpoints.
13. **A1** Document CRM in `openapi.yaml`; add contract tests.
14. **CON-2** Unique `(workspace_id,email)` partial index + upsert-on-import.
15. **CC-3** Real pagination (cursor/page params end-to-end).
16. **FE-3** Build (or honestly gate) the Documents workbench; remove dead-end links.

**P3 — Polish & scale:**
17. **CC-7** Async/batched, transactional CSV import. **DEAL-5** deal↔project
    back-sync. **FE-4** unify on `authFetch`; fix token/design-law nits. **CC-6**
    owner/assignment model for contacts/deals.

### Quick wins (high value / low effort)
D4 (one migration), CON-4/DEAL-3/LEAD-3 (a `RowsAffected` check each), DEAL-2 (a few
`Notify` calls — dispatcher exists), validation (`400`s), and FE edit/delete wiring
close the most visible end-to-end gaps cheaply.
