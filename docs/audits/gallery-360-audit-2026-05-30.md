# RawDrive Gallery — 360° End-to-End Audit

> **Date:** 2026-05-30  ·  **Scope:** Gallery feature + all sub-features (albums, proofing, public sharing, favorites, downloads, analytics, commerce, FaceID, design studio, watermarking)  ·  **Method:** Read-only multi-agent code/architecture/security audit, adversarially verified. No live testing.  ·  **Branch:** main

Finding counts — Critical: 12 · High: 35 · Medium: 47 · Low: 36 · Info: 14

## Executive Summary

The Gallery 360 audit assessed eight dimensions and surfaced **144 verified findings**: **12 Critical, 35 High, 47 Medium, 36 Low, and 14 Informational**. The headline conclusion is unambiguous: **the gallery subsystem is not safe to operate multi-tenant in production today.** The same structural defect — *authorization is asserted at the route mount but never enforced at the object level* — recurs across the API, security, storage, and data layers, which is why the Critical count clusters in exactly four dimensions (Backend API, Security & Authorization, Data Model, Test Coverage). These are not eight independent problems; they are one missing access-control spine observed from eight vantage points.

The most severe systemic risk is **cross-tenant Broken Object-Level Authorization (BOLA/IDOR)**. Gallery, album, proofing, and access-control handlers take no workspace parameter and perform no ownership check (`API-SEC-01`, `SEC-IDOR-01/03/04/05`). Any authenticated photographer can read, modify, or **delete any other studio's galleries, albums, and proofing data** by guessing or enumerating UUIDs. The intended database backstop does not exist: RLS is effectively inert because there is no `FORCE ROW LEVEL SECURITY`, the app connects as the table owner (which bypasses RLS), and the per-request workspace GUC is set on a *different pooled connection* than the one that runs the query (`DB003-01`, `DB003-02`, `SEC-RLS-01`). So both the application-layer check and the database-layer backstop are simultaneously absent. This is a tenant-isolation failure of the highest order for a multi-studio SaaS.

The second systemic risk is a **non-enforcing public access model.** The gallery password gate is validated *nowhere* on the asset and download paths (`SEC-AUTH-01`, `API-SEC-02`); the gate is effectively client-side decoration — the public page fetches and renders the full asset list and thumbnail URLs server-side, then merely visually hides them behind a JavaScript gate (`UI-14`, `PERF005-D`). Share-link controls (PIN, password, expiry, access-count) are likewise unenforced on the slug-addressed serving path (`SEC-AUTH-02`). Combined with **no per-gallery brute-force throttle** on the password endpoint (only a coarse ~600/min global IP limiter, `API-SEC-05`, `SEC-RATE-01`) and **anonymous, unauthenticated, un-rate-limited public thumbnail serving** (`STO-03`, `STO-04`), the platform exposes private client galleries to enumeration and scraping at scale. The frontend even handles a `429` the backend never emits (`TEST001-15`) — a coverage gap that masked the missing control.

The third systemic risk is **data-at-rest exposure.** Application-layer encryption-at-rest for gallery imagery is **dead code**: originals and WebP derivatives are stored and served without RawDrive-controlled ciphertext, while the `EncryptionService`, the `assets.is_encrypted`/`encryption_key_id` columns, and the `encryption_keys` table are never written or referenced (`SEC-CRYPTO-01`, `ENC-01`, `ENC-02`, `DB004-01`). B2/S3 server-side encryption may be configurable via `STORAGE_SSE_MODE`, but that is not the strict enterprise/uploader contract: **all originals and all WebP derivatives, including thumbnails, need RawDrive-tracked encryption metadata and decrypt-on-serve after authorization is fixed.** Compounding this, the storage proxy authenticates the JWT but never scopes the requested object key to the token's workspace (`API-SEC-03`, `STO-02`), so a valid token for studio A can fetch studio B's full-resolution derivatives. Full-access JWTs are also transported in `?token=` query strings on image `src` URLs (`API-SEC-04`, `LB-01`, `SEC-LEAK-01`), leaking credentials into logs, referrers, and caches.

Beyond security, **performance will not scale** and **the quality safety net is largely missing.** N+1 patterns dominate the hot paths — public `ListAssets` does a per-asset `GetByID` with no batch fetch or pagination, the dashboard hydrates one HTTP request per asset, and the synchronous ZIP export buffers full files in the request path (`PERF001-A/B/D`). Grids render every asset with no virtualization (`PERF002-A`). A CDN-cacheable immutable thumbnail endpoint exists but the frontend never calls it, so every preview byte transits the API node marked private (`PERF005-A`, `STO-04`). On the quality side, the **two handlers with the worst security exposure have zero tests** (`TEST001-01/02` — Critical), the public guest journey and proofing workflow have no E2E coverage (`TEST007-01/02`), and existing tests include tautologies (`expect(true).toBeTruthy()`, `toHaveTitle(/.*/)`) and E2E auth anti-patterns the house rules explicitly forbid (`TEST002-03`, `TEST008-01`, `TEST003-01/02`).

The frontend and lightbox dimensions are materially healthier — no Criticals — but carry real correctness debt and a token-rendering regression. A cluster of **undefined design tokens** (`accent-primary-contrast`, `danger`/`accent-danger`, shadcn-convention `*-foreground` leaks) renders **colorless text on primary public CTAs, the proofing checkmark, and the guest password-gate error** (`UI-01/03/04`), and a route is hard-forced to dark theme in violation of the theme-resolution rule (`UI-02`). The dashboard proofing toolbar and `1/2/3` shortcuts are dead (`onProofingAction` never wired, `LB-02`), and the comments sidebar is hardcoded to "No comments yet" and never fetches (`LB-05`) — two shipped-but-broken features. Eight orphan gallery components were shipped with zero non-test importers (`UI-07`).

**Bottom line for engineering leadership:** treat this as a **security incident-grade remediation, not a backlog grooming exercise.** The platform should be considered to have *no effective tenant isolation and no effective public access control* until the P0 items below are closed. The encouraging news is leverage: a single, well-placed object-level authorization layer (workspace-scoped service signatures + a properly enforced RLS configuration as defense-in-depth) collapses the majority of the Critical and High findings at once. The roadmap is sequenced so that P0 buys back tenant safety in days, not quarters.

### Top Risks

- Cross-tenant BOLA/IDOR is exploitable today: gallery, album, proofing, and access-control handlers take no workspace parameter and never check ownership, so any authenticated photographer can read, modify, or DELETE any other studio's galleries and assets by UUID enumeration (API-SEC-01, SEC-IDOR-01/03/04/05). This is a total tenant-isolation failure.
- The database backstop does not work: RLS is inert because there is no FORCE ROW LEVEL SECURITY, the app connects as the table owner (bypassing RLS), the per-request workspace GUC is set on a different pooled connection than the query runs on, and 16 gallery sub-tables have no policy at all (DB003-01/02/03, SEC-RLS-01). App-layer AND db-layer isolation are simultaneously absent.
- The public password gate and share-link controls are non-enforcing: the gallery_session/PIN/password/expiry/access-count are validated nowhere on the asset and download paths, and the page server-renders the full asset list behind only a client-side visual gate (SEC-AUTH-01, SEC-AUTH-02, API-SEC-02, UI-14). Private client galleries are effectively public.
- Application-layer encryption-at-rest is dead code while the enterprise uploader contract requires it: originals and every WebP derivative, including public thumbnails, need RawDrive-tracked encryption metadata and decrypt-on-serve, but the EncryptionService plus is_encrypted/encryption_key_id columns and encryption_keys table are never written (SEC-CRYPTO-01, ENC-01/02, DB004-01).
- The storage proxy authenticates the JWT but never scopes the object key to the token's workspace, and full-access JWTs ride in ?token= query strings on image src URLs — a token for studio A fetches studio B's full-res derivatives, and credentials leak into logs/referrers/caches (API-SEC-03, STO-02, API-SEC-04, SEC-LEAK-01, LB-01).
- Public password-gate brute force and thumbnail scraping are wide open: no per-gallery throttle (only a coarse ~600/min global IP limiter) and anonymous, unauthenticated, un-rate-limited public thumbnail serving with an inverted/no-CDN cache policy (API-SEC-05, SEC-RATE-01, STO-03, STO-04). The frontend even handles a 429 the backend never emits.
- Deployment/configuration drift can quietly undo hardening work: the env examples had still documented Cloudflare R2 / `STORAGE_DRIVER=r2` while the current storage factory only supports `s3` for the managed B2 backend. This review updates those examples, but the weak link remains important: config examples, launch checklists, key-management docs, and gallery/uploader audits must stay aligned on B2, SSE baseline, app-layer media encryption, rate-limit knobs, and the decrypt-proxy/cache contract (CFG-01/02/03 below).
- Download delivery is under-modeled for a production client gallery product: current public single-photo download streams originals only, authenticated dashboard download bypasses the download API, bulk ZIP is synchronous/under-validated, and the photographer cannot define a clear policy for original vs WebP, watermark vs no watermark, multi-select, or full-gallery export. This must become a server-enforced gallery/share policy, not a client menu convention.
- The quality safety net that should have caught all of the above is missing: the two highest-risk handlers (GalleryHandler.GetByID, AlbumHandler.GetByID) have ZERO tests, the guest and proofing E2E journeys are uncovered, and existing tests include tautologies (expect(true).toBeTruthy(), toHaveTitle(/.*/)) plus forbidden E2E UI-login patterns (TEST001-01/02, TEST007-01/02, TEST008-01, TEST002-03, TEST003-01/02).
- Performance will collapse under real gallery sizes: pervasive N+1 on public ListAssets and dashboard hydration, synchronous full-file-buffering ZIP export and synchronous per-view analytics on the request path, and no grid virtualization, while a CDN-cacheable immutable thumbnail endpoint exists but is never called (PERF001-A/B/D, PERF002-A, PERF005-A/C).
- Shipped-but-broken features erode trust at the worst moment: the dashboard proofing toolbar and 1/2/3 shortcuts are dead (onProofingAction never wired) and the comments sidebar is hardcoded to 'No comments yet' and never fetches (LB-02, LB-05); undefined design tokens render colorless text on primary public CTAs, the proofing checkmark, and the guest password-gate error (UI-01/03/04).

## Frontend UI/UX, Components & Design-Token Compliance

**Posture:** At-risk — verified against live code. The root cause is systemic: Tailwind v4 here has no `tailwind.config`, no safelist, and no `@utility`/`@layer` custom definitions, so any `text-/bg-/border-/ring-/shadow-<name>` whose backing `--color-<name>`/`--shadow-<name>` is absent from the `globals.css` `@theme` block is simply never generated and the element silently inherits. This produces colorless text/icons on real guest-facing surfaces (cover/design-studio route, the public commerce surface, the unlock-gallery and FaceID CTAs, the proofing checkmark) plus a cluster of accessibility gaps and one presentation-only password gate. Two findings were downgraded after confirming their citations land in dead or dark-forced code (UI-03 High→Medium, UI-06 Medium→Low). The cover route (UI-02) and the reachable commerce surface (UI-04) are the most material live defects.

### API-SEC-03 — Storage proxy never scopes object key to the token's workspace

- **Severity:** Critical · **Category:** Authorization · **Confidence:** High
- **Evidence:** `cmd/api/main.go:2312-2380` `GET /storage/*` — for non-thumbnail keys it parses the bearer/`?token=` JWT (:2340 `jwtSvc.ParseAccessToken`) then calls `storageProvider.Get(ctx, key)` (:2346) with the raw client-supplied key. ### API-SEC-04 — Access token accepted as `?token=` query parameter on storage proxy

- **Severity:** High · **Category:** Security / contract · **Confidence:** High

#### SEC-IDOR-01 — Gallery mutate/delete endpoints lack workspace ownership check (BOLA)
- **Severity:** Critical · **Category:** Broken Access Control (OWASP A01:2021) · **Confidence:** High
- **Evidence:** `backend/internal/handler/gallery_handler.go:597` — `SoftDelete` parses `{id}` and calls `h.gallerySvc.SoftDelete(r.Context(), id)` at `:604` with no workspace check (verified: handler ends at `:609` with no guard). #### SEC-RLS-01 — RLS is not a reliable backstop
- **Severity:** High (reclassified from Critical) · **Category:** Security Misconfiguration / Broken Access Control (OWASP A05/A01:2021) · **Confidence:** High
- **Evidence:** (1) No `FORCE ROW LEVEL SECURITY` anywhere — grep across migrations returns none; the runtime connects via `pgxpool.ParseConfig(DATABASE_URL)` (`main.go:701`). **Evidence correction:** the original "POSTGRES_USER (docker-compose.yml:10)" cite is imprecise — compose uses `${PROJECT_USER}`/`${PROJECT_PASSWORD}` (`docker-compose.yml:10-11`) and the runtime role is whatever `DATABASE_URL` specifies; migration 008 creates `rawdrive_app` only as a separate NOLOGIN role "for RLS testing" (`008:1-9`), so the app does NOT run as the non-owner role by default — a table-owner/superuser bypasses RLS without `FORCE`. (2) `SetWorkspaceID` uses `set_config('app.workspace_id', $1, false)` (`db_context.go:31`); `is_local=false` makes it SESSION-scoped, and no pool `AfterRelease`/`BeforeAcquire`/`DISCARD`/`RESET` hook exists in production code (grep returns only test files). (3) Coverage gaps confirmed: `migration 061:29-31` lists `gallery_analytics_daily` as NOT covered; `albums`, `album_assets`, `gallery_assets`, `proofing_sessions`, `proofing_selections`, `proofing_comments`, `album_approvals`, `gallery_access_logs`, and `gallery_favorites` have NO `ENABLE ROW LEVEL SECURITY` in 008 or 061 (verified absent).
- **Impact:** RLS cannot be relied upon as the backstop for the handler-level IDORs. Under the table-owner role (no `FORCE`) it is bypassed entirely; the session-var-on-pooled-connection design is fragile; and the most IDOR-exposed tables have no policy at all. Reclassified High because it is a defense-in-depth failure, not a standalone breach without the handler IDORs.
- **Recommendation:** Run the app as a non-owner role with `ALTER TABLE … FORCE ROW LEVEL SECURITY` on every tenant table. Set the tenant GUC transaction-locally (`set_config(…, true)`) in the same transaction as each query, or add a pool `AfterRelease` hook to `RESET app.workspace_id` / `DISCARD ALL`. Extend RLS (FK-walking `USING` clauses) to `albums`, `album_assets`, `gallery_assets`, `proofing_*`, `album_approvals`, `gallery_access_logs`, `gallery_analytics_daily`, and `gallery_favorites`. Do not treat RLS as a substitute for handler-level authorization.

### Cross-Finding Narratives

- **Deleted-content-still-served chain (`STO-02` + `STO-03` + `ACC-02`).** A deleted asset's thumbnails remain anonymously fetchable (`main.go:2326`), its derivatives remain in B2 (`asset_purge_worker.go:110-111` deletes only the recording rows, not the objects), and its full-res `display_webp` is cross-tenant readable via the edge IDOR (`edge_delivery_handler.go:53`). Fixing `ACC-02` (delete derivative objects) closes both the orphan-cost and the deleted-content-serve legs; fixing `STO-02` closes the cross-tenant leg.
- **Three half-built at-rest mechanisms, all effectively off (`ENC-01` + `ENC-02` + `SSE-01`).** The codebase ships an app-level `EncryptionService` envelope, SSE-B2 via `STORAGE_SSE_MODE`, and SSE-C — and runs with ALL three disabled by default. This is the central narrative for the encryption dimension: marketing/compliance posture implies at-rest encryption; runtime delivers B2 transparent-disk only. A single startup assertion logging the effective at-rest mode, plus one `AGENTS.md` section declaring the canonical model, would resolve the ambiguity.

### Enhancements

- **Centralize storage-key derivation.** The public-thumbnail anonymous branch and the edge handler both reconstruct keys with the same `fmt.Sprintf` pattern (`thumbnail_service.go:308` vs `edge_delivery_handler.go:47-50`) instead of sharing a single helper (a shared helper is referenced in comments at `thumbnail_service.go:303`). If the public/auth prefix split ever changes, the two call sites can drift and silently re-expose `display_webp` under the public prefix. Export one key-derivation function used by the service, worker, edge handler, and the `/storage` allow-list (ties into `STO-05`).
- **Fix stale provenance label.** The legacy direct-upload path hardcodes `StorageDriver:"r2"` on the asset row (`upload_service.go:99`) even though the managed backend is Backblaze B2 — an incorrect provenance label on every legacy-path asset. Cosmetic/Info, but worth correcting for data-lineage accuracy and consistency with the B2 migration.
- **Add a self-healing storage-recompute job.** A periodic job that re-derives `used_bytes`/`derivative_bytes` from `assets` + `asset_derivatives` would heal historical drift from `ACC-01` and detect orphans from `ACC-02`/`WORKER-01` in the same pass.
- **Single caching contract.** Define one shared caching policy (`private` for authed originals/display, `public, immutable` for anonymous content-addressed thumbnails behind a CDN) consumed by both `edge_delivery_handler` and the `/storage` proxy, eliminating the inverted policy across `STO-01` and `STO-04`.
- **Startup at-rest assertion.** Emit one unambiguous startup log line declaring the effective at-rest encryption mode (app-envelope / SSE-B2 / SSE-C / plaintext), and FATAL when `APP_ENV=production` resolves to plaintext — converting the silent `ENC-01` gap into a deploy-time gate.

## Data Model, Migrations & Integrity

**Posture:** CRITICAL — Tenant isolation has **no database backstop**. RLS is *doubly* inert: (1) no table has `FORCE ROW LEVEL SECURITY` and the app connects as the table owner, which bypasses non-FORCE RLS entirely; and (2) the per-request `app.workspace_id` GUC is set on a *different* pooled connection than the query runs on. Most findings independently verified during this review; DB001-01 and DB004-03/04/05 were corrected or downgraded after checking the code directly.

### DB003-01 — RLS effectively inert in production: no FORCE ROW LEVEL SECURITY + app connects as table owner

- **Severity:** Critical · **Confidence:** High · **Category:** RLS
- **Evidence:**
  - `grep 'FORCE ROW LEVEL SECURITY' backend/internal/database/migrations/` returns **zero** matches (independently re-confirmed in this review).
  - `backend/cmd/.../main.go:701-712` builds the pool from `DATABASE_URL` setting only `MaxConns=25`/`MinConns=5` — no `AfterConnect`/`AfterAcquire` hook; production code never issues `SET ROLE rawdrive_app` (that string lives only in `backend/internal/.../test_helpers.go:82,113,153,166,205`).
  - `docker-compose.yml:10` `POSTGRES_USER: ${PROJECT_USER}` is the DSN role and **owns every table**.
  - `008_create_rls.up.sql:20-48` and `061_rls_extension_f009.up.sql:46-204` only `ENABLE` (never `FORCE`) RLS; every policy carries an `app.bypass_rls='on'` escape hatch (`008:32`, `061:94`).
- **Impact:** A table owner/superuser **bypasses non-FORCE RLS**, so these policies never constrain the app's own queries. All workspace isolation in production rests solely on handler-level `workspace_id` filters. Any repo path that omits the filter has zero DB backstop — confirmed examples: `GalleryRepo.GetByID` (`gallery_repo.go:205`) and `AlbumRepo.GetByID` (`album_repo.go:66`) query by `id` alone with no workspace predicate. RLS provides **false assurance** (OWASP A01: Broken Access Control). Note: `bypass_rls` is never set in app code (only `test_helpers.go` + the m35 integration test), so the escape hatch itself is not the exposure — the missing FORCE plus the owner role is.
- **Recommendation:** Add `ALTER TABLE … FORCE ROW LEVEL SECURITY` to every RLS-enabled table in a new migration **and** make the app connect as the non-owner `rawdrive_app` role (a dedicated low-privilege DSN, or an `AfterConnect` hook issuing `SET ROLE`), so policies actually bind. Fix DB003-02 in the same change or FORCE will lock the app out (see Enhancements / sequencing trap).

### DB003-02 — Per-request workspace context is set on a different pooled connection than the query runs on

- **Severity:** Critical · **Confidence:** High · **Category:** RLS
- **Evidence:**
  - `db_context.go:29-37` runs `d.pool.Exec(ctx, "SELECT set_config('app.workspace_id', $1, false)", workspaceID)` against a `*pgxpool.Pool` with `is_local=false` (session-scoped, not transaction-scoped). `pool.Exec` acquires an arbitrary connection, sets the var, and releases it.
  - Called once per request at `middleware.go:159` `_ = db.SetWorkspaceID(...)` with the **error discarded**.
  - Repos do **not** pin a connection: `gallery_repo.go` and `album_repo.go` use bare `r.pool.Exec/Query/QueryRow` (9 and 8 occurrences respectively) and never call `.Acquire()`. Re-confirmed in this review: `grep '\.Acquire(' backend/internal/repository` returns **nothing**. The follow-up query therefore acquires a potentially different connection where `app.workspace_id` is empty.
- **Impact:** Even if RLS were FORCEd, the `USING` clause `workspace_id::text = current_setting('app.workspace_id', true)` would compare against an empty/stale value on most queries (`current_setting(...,true)` returns `''` when unset → matches nothing), so RLS would unpredictably deny-all or, combined with DB003-01, simply not engage. Confirms RLS cannot be trusted as a control **as currently wired**.
- **Recommendation:** Set the GUC transaction-locally (`set_config(…,true)`) inside the same transaction/connection that runs the query, OR acquire a dedicated `*pgxpool.Conn` per request and pin all repo queries to it. Stop discarding the error at `middleware.go:159`.

## Performance & Scalability

**Posture:** At risk for scale. The gallery feature carries a systemic read-side N+1 across its highest-traffic public and dashboard paths (per-asset `GetByID`), ships unbounded list payloads with no pagination, renders unvirtualized DOM, and applies weak HTTP/CDN caching — all of which degrade linearly with photos-per-gallery and concurrent viewers. The two highest-impact items (public `ListAssets` N+1, public grid non-virtualization) are confirmed real and mandatory before scale; several originally-Critical projections are downgraded where the latency/limiter math is unmeasured rather than observed. A ready-made immutable edge-delivery endpoint already exists but is unwired, and a synchronous analytics insert is mislabeled "fire-and-forget" — both are genuine low-effort wins. **Enhancements**

- **Single batch primitive retires four findings.** The read-side N+1 (per-asset `GetByID`) is the same root cause across PERF001-A (public), PERF001-B (dashboard), and PERF001-D (ZIP), and is amplified by PERF001-C/E. Prioritize this over per-finding fixes.
- **Sequence pagination before virtualization.** PERF001-A (unbounded payload) and PERF002-A (unbounded DOM render) are inverse-coupled — API keyset/cursor pagination is a prerequisite for client virtualization to bound both bytes and DOM. Ship API cursor pagination first, then `react-window`/`virtua` on the grid.
- **NEW (discovered): album filter runs the N+1 twice.** `frontend/src/app/g/[slug]/page.tsx:109-111` issues a SECOND full asset-list fetch when an album filter is active — `totalAssetCount = albumId ? (await getPublicGalleryAssets(slug, undefined, ws)).length : assets.length`. Filtering by an album thus runs the PERF001-A N+1 twice per render (album-scoped list + gallery-wide count). A COUNT-only endpoint for the "All Photos" chip removes the second N+1 entirely.
- **NEW (discovered): storage proxy serves no Content-Length and no Range.** `backend/cmd/api/main.go:2360-2379` streams via `io.Copy(w, rc)` with no `Content-Length` and no Range support — every thumbnail/display/original is a non-resumable, non-byte-range chunked response, defeating browser/CDN partial caching and breaking seek for any video/original served through `/storage/*`. - **NEW (discovered): the immutable edge endpoint is ready and unwired.** `backend/internal/handler/edge_delivery_handler.go` already implements `public, max-age=86400, immutable` + `X-Content-Type-Options: nosniff` and an `asset_derivatives` lookup with a `thumbnails/<id>/` vs `derivatives/<id>/` split. ## Appendix A — Encryption-at-Rest Design for Gallery Derivatives

> Scope: encryption-at-rest for gallery image bytes (originals + WebP/JPEG derivatives) stored on Backblaze B2 and served through the authenticated `/storage/*` proxy. This appendix documents the *actual* state of the codebase (which is more nuanced than "no encryption"), the threat model, a recommended target design, performance budget, and a phased backfill path. Every claim is cited to a real file.

### A.0 Executive summary

The codebase contains **two independent encryption-at-rest mechanisms, in two opposite states of maturity**:

1. **Server-side encryption (SSE) — LIVE and production-deployed.** The real AWS-SDK S3 client (`backend/internal/storage/s3_aws.go`) sends SSE headers on every `PutObject` / `CreateMultipartUpload` / `UploadPart` and (for SSE-C) on every `GetObject`, driven by `STORAGE_SSE_MODE` / `STORAGE_SSE_C_KEY` read in `backend/cmd/api/main.go:1173-1174`. A dedicated migrator, `backend/cmd/encrypt-existing/main.go`, re-wraps existing objects; its header docstring records a completed pass on **2026-05-20 (505/505 objects copied to SSE-B2)**.
2. **App-layer envelope encryption — DEAD code.** `backend/internal/service/encryption_service.go` (`EncryptFile` / `DecryptFile`, per-workspace DEK wrapped by a master KEK) is never instantiated in `cmd/api/main.go`; the `assets.is_encrypted` / `assets.encryption_key_id` columns (migration `044_m11_deferred_features.up.sql:22-23`) are referenced by **zero** Go code; the `encryption_keys` table (same migration, RLS in `061_rls_extension_f009.up.sql:53`) is never written or read at runtime.

So the precise, defensible statement is **not** "gallery images are unencrypted at rest." It is: **gallery derivatives are protected at rest only by whatever `STORAGE_SSE_MODE` is configured to (server-side), while the application-layer envelope-encryption feature that the schema was built for was never wired up.** The user's phrase "decrypting of webp images in the gallery" maps to a decrypt step that *exists in two forms but neither is app-controlled on the serve path*: SSE-C decrypt happens transparently inside `storageProvider.Get`, and the app-layer `DecryptFile` is never called.

**Alignment update:** the upload E2E review in `docs/audits/photo-upload-e2e-review-2026-05-30.md` sets the stricter enterprise contract for media: **all originals and all WebP derivatives, including small thumbnails, must be encrypted at rest with RawDrive-tracked encryption metadata and served only through an authorization-checked decrypt proxy.** That supersedes the older "leave `thumbnails/*` out of app-layer encryption for anonymous CDN serving" trade-off in this appendix. SSE remains a useful baseline/backstop, but it is not sufficient by itself for the enterprise promise.

### A.1 Current state (precise)

#### A.1.1 The serve path and the public-thumbnail bypass

The storage proxy is `GET /storage/*` in `backend/cmd/api/main.go:2312-2380`:

- `isPublicThumbnail := strings.HasPrefix(key, "thumbnails/")` (`main.go:2326`). If true, **no JWT is required** — the handler skips straight to `storageProvider.Get(...)` (`main.go:2346`).
- Everything else (`derivatives/...` incl. `display_webp`, and `<workspace>/<upload>/original.<ext>`) requires a Bearer header **or** `?token=<jwt>` (`main.go:2329-2343`).
- The handler does `io.Copy(w, rc)` of whatever `storageProvider.Get` returns (`main.go:2376`), guessing content-type from the extension (`main.go:2363-2374`). **It performs no decryption itself** — decryption, if any, is entirely inside the storage driver.

Key-prefix split is set at generation time in `backend/internal/service/thumbnail_service.go`:
- `thumb_sm_webp` / `thumb_md_webp` / `thumb_lg_webp` → `thumbnails/<assetID>/<name>.webp` (public).
- `display_webp` (2400px) and `watermark_preview` → `derivatives/<assetID>/<name>.webp` (auth). Confirmed by `thumbnail_service_test.go:28-33,126-134`.
- JPEG thumbs are written under `thumbnails/<id>/<name>.jpg` via `generateOne` (`thumbnail_service.go:211-216`).

`edge_delivery_handler.go:43-59` mirrors the same prefix logic and serves through `thumbnailSvc.GetStore().Get(...)` (it can optionally apply a watermark in-process at `:69-86`).

**Implication for any at-rest scheme:** the byte path for a public thumbnail is `anonymous HTTP GET → storageProvider.Get(key) → io.Copy`. Whatever encryption is applied to `thumbnails/*` objects MUST be reversible *without any per-user secret*, because the caller is anonymous. SSE-B2/SSE-S3 (server-managed key) satisfies this; SSE-C and app-layer DEK encryption do **not** unless the secret lives server-side in the proxy process (which it does for SSE-C and could for app-layer).

#### A.1.2 SSE — the live mechanism

`backend/internal/storage/s3_aws.go`:
- `newAWSS3Client` maps `STORAGE_SSE_MODE` to a typed enum and fails fast on unknown values (`s3_aws.go:83-100`). Accepted: `""` (off), `AES256` (SSE-B2/SSE-S3), `aws:kms`, `SSE-C`.
- For `SSE-C` it validates `STORAGE_SSE_C_KEY` is 64-hex / 32 bytes at startup, precomputes base64 key + MD5 (`s3_aws.go:109-133`).
- `PutObject` sets `ServerSideEncryption` when `c.sse != ""` and adds `SSECustomerKey*` headers when `sseCActive` (`s3_aws.go:181-192`). The comment at `:176-180` explicitly notes this single code path "also encrypts every derivative" the thumbnail pipeline writes.
- `GetObject` re-sends the SSE-C key headers so B2 decrypts on the fly (`s3_aws.go:206-215`). **This is the only "decrypt webp" that runs today** — and it is invisible to the gallery code.
- Multipart (chunked upload) wires SSE on `CreateMultipartUpload` and each `UploadPart` (`multipart.go:75-92,114-121`).
- `PresignGetObject` notes presigning is effectively unused in production because serving goes through the JWT-gated `/storage/*` proxy (`s3_aws.go:242-248`).

`STORAGE_SSE_MODE` / `STORAGE_SSE_C_KEY` are sourced in `main.go:1165-1174`. The `storage.Config` struct documents all four modes (`config.go:18-39`). The legacy/local-fallback `s3.go` driver does **not** apply SSE (no references), so SSE is a property of the AWS-SDK client path only — confirm production uses that path.

#### A.1.3 App-layer envelope encryption — the dead mechanism

`backend/internal/service/encryption_service.go`:
- `NewEncryptionService` reads `ENCRYPTION_MASTER_KEY` (base64, 32 bytes) and returns **`nil`** if unset (`encryption_service.go:27-38`). Note this is a **different env var from `PLATFORM_SETTINGS_KEK`** (the KEK used by platform-settings + TOTP via `backend/internal/crypto/envelope.go` and `main.go:728,867`). The two key systems are unrelated.
- `GenerateDEK` / `GetActiveDEK` create and unwrap per-workspace DEKs stored in `encryption_keys` (`encryption_service.go:41-72`).
- `EncryptFile` / `DecryptFile` do AES-256-GCM with a random 12-byte nonce prepended to the ciphertext (`encryption_service.go:74-138`).
- **Dead-code proof:** `grep NewEncryptionService backend/cmd/api/main.go` → no match. `grep is_encrypted|encryption_key_id backend --include=*.go` → no match. The columns from `044_m11_deferred_features.up.sql:22-24` and the `encryption_keys` table are schema-only.

**Two latent defects in the dead code that MUST be fixed before reuse:**
1. **Not streaming.** Both `EncryptFile` (`:86 io.ReadAll`) and `DecryptFile` (`:116 io.ReadAll`) buffer the entire object into memory. For 2400px `display_webp` (~0.3–1.5 MB) this is tolerable, but for **originals** (RAW/JPEG, 20–60 MB+) under concurrency it is a memory-pressure / OOM risk. The AWS `PutObject` path already buffers once for SigV4 seekability (`s3_aws.go:148-161`); stacking a second full buffer doubles it.
2. **Key derivation mismatch / operational footgun.** Using `ENCRYPTION_MASTER_KEY` instead of the established `PLATFORM_SETTINGS_KEK` means a third master secret to provision, rotate, and back up — and silent disablement (`return nil`) means a missing env var degrades to plaintext with only a `slog.Warn`, no FATAL. Contrast with `PLATFORM_SETTINGS_KEK`, which FATALs in production (`main.go:739`).

### A.2 Threat model — what at-rest encryption does and does not buy here

Because serving already flows through an authenticated app proxy (`/storage/*`) rather than public bucket URLs, the marginal value of at-rest encryption is narrower than it first appears. Enumerate the adversaries:

| # | Adversary / scenario | SSE-B2/S3 (server key) | SSE-C (customer key, server-held) | App-layer DEK envelope | Notes |
|---|---|---|---|---|---|
| T1 | Someone steals raw B2 disks / B2 ops insider reads the block store | ✅ ciphertext | ✅ ciphertext | ✅ ciphertext | All three defeat physical-media theft. This is the *only* threat SSE-B2 meaningfully adds over B2's baseline. |
| T2 | B2 account/API-key compromise (leaked `B2_KEY_ID`/`B2_APPLICATION_KEY`) | ❌ attacker GETs plaintext (key transparent) | ✅ attacker gets ciphertext (lacks SSE-C key) | ✅ attacker gets ciphertext (lacks DEK+KEK) | The decisive differentiator. SSE-B2 is useless here because B2 decrypts for any authenticated caller. |
| T3 | Stolen RawDrive app secrets file (`.env`) — both B2 creds *and* the SSE-C/KEK key | ❌ | ❌ | ❌ | If the attacker has the app's own key material, no at-rest scheme helps. Mitigate with a KMS/HSM so the key never sits in plaintext on app hosts. |
| T4 | IDOR / broken authz in the app (e.g. the V2/V5 storage-proxy + asset-IDOR findings in `docs/security/2026-05-30-full-application-security-audit.md`) | ❌ | ❌ | ❌ | At-rest encryption is the wrong control. The proxy/driver decrypts for *any* request it serves, so an authz bypass returns plaintext regardless. **Fix authz, not crypto.** |
| T5 | Anonymous read of `thumbnails/*` (legacy design) | ✅ still works | ✅ still works (server holds key) | ⚠️ replaced by decrypt-proxy | Enterprise contract retires direct anonymous object serving. Public thumbnails still display to authorized gallery visitors, but through a short-lived gallery/share scoped decrypt URL after password/share/expiry checks. |
| T6 | Tenant-isolation: one workspace's key compromise must not expose another's | ⚠️ single key for all | ⚠️ single key for all | ✅ per-workspace DEK | Only the app-layer envelope gives per-tenant cryptographic isolation (`encryption_keys.workspace_id`). |

**Conclusions that drive the recommendation:**
- The real residual risk that at-rest crypto closes is **T2 (B2 credential compromise)** and **T6 (per-tenant isolation)**. SSE-B2 closes *neither* (T2) — only **SSE-C** or **app-layer envelope** does, because both keep the decryption secret out of B2.
- **SSE-C is the lowest-code upgrade** that closes T2 for all objects, but it is an operational footgun: lose `STORAGE_SSE_C_KEY` and **every object is unrecoverable** (`config.go:33-37`; the migrator surfaces `stateWrongSSECKey` objects loudly, `encrypt-existing/main.go:205-209`). Use it only with KMS/escrow/rotation/restore drills; otherwise use SSE-B2/AES256 as a baseline backstop while the app-layer contract is built.
- **App-layer envelope is required for enterprise-grade media protection** because it gives RawDrive-owned encryption metadata, per-object/per-workspace keying, and a consistent decrypt-on-serve path across originals, display WebP, ZIP exports, edge delivery, and thumbnails. It must be sequenced **after** authorization fixes, or the decrypt proxy will turn existing IDORs into plaintext cross-tenant leaks.

### A.3 Recommended design

**Tiered model — match the control to the threat, do not over-encrypt the public path.**

#### Tier 0 (baseline, all tenants) — server-side encryption backstop
Keep the already-built SSE path enabled as a baseline while the stricter app-layer work lands:
- Set `STORAGE_SSE_MODE=AES256` for the managed B2 default unless the team has completed SSE-C escrow/rotation/restore drills. `SSE-C` is acceptable only with KMS/secret-manager custody and a tested key-loss runbook.
- This protects every object at the storage-provider layer with very little app cost, but it does **not** replace RawDrive-owned encryption metadata or decrypt-on-serve. It is a backstop, not the enterprise media-encryption finish line.
- Harden the startup contract: in production, log the effective media at-rest mode and FATAL if no storage encryption baseline is configured.

#### Tier 1 (enterprise production target) — app-layer streaming envelope on ALL media objects
For the enterprise production-grade contract, layer streaming app encryption over **originals and every derivative, including `thumbnails/*`**.

- **Key hierarchy.** Per-asset DEK (or per-workspace DEK as the table is currently shaped) → wrapped by a workspace KEK → wrapped by the platform master KEK. Reuse the existing envelope discipline: standardize on **`PLATFORM_SETTINGS_KEK`** (already FATAL-guarded, already used by `crypto/envelope.go`) and **retire the orphan `ENCRYPTION_MASTER_KEY`** in `encryption_service.go:28` to avoid a third master secret. Store wrapped DEKs in `encryption_keys.encrypted_dek` (already the schema, `044:12`).
- **Algorithm / nonce.** AES-256-GCM, random 96-bit nonce per object, nonce prepended to ciphertext (the dead code already does this, `:98-103`/`:128-132`). Add the **storage key + variant + workspace_id as GCM AAD** so a ciphertext copied to a different object key fails authentication (prevents object-substitution within the bucket).
- **Where to encrypt — upload + derivative generation.** Encrypt originals at finalize/source-upload and wrap every `thumbnail_service.go` `s.store.Put(...)` call, including `generateOne`/`thumbnails/*` and `generateWebPDerivative`/`derivatives/*`. Each object should carry algorithm, version, nonce/chunk framing, and key reference metadata; `asset_derivatives` needs per-row encryption metadata, not just `assets`.
- **Where to decrypt — every serving path.** In `/storage/*` (`main.go:2346`), `edge_delivery_handler.go:59`, authenticated asset downloads, public asset downloads, and ZIP export, resolve the asset/derivative row, enforce workspace/gallery/share/password/expiry permission first, then stream-decrypt before `io.Copy`. Public gallery thumbnails must use short-lived gallery/share scoped decrypt URLs rather than the current anonymous `thumbnails/*` bypass.
- **Make `DecryptFile`/`EncryptFile` streaming** (replace `io.ReadAll` at `:86`/`:116` with an AES-GCM streaming construction — chunked GCM with per-chunk nonces, or switch to a streaming AEAD such as `age`/STREAM/Tink) before wiring originals, to remove the OOM risk in A.1.3.
- **Key storage + rotation.** `encryption_keys.key_version` + `rotated_at` already exist (`044:13,16`). Rotation = `GenerateDEK` (new version) for new writes; old objects keep their `encryption_key_id` until lazily re-encrypted on next access or via a backfill job (Section A.5). RLS on `encryption_keys` exists (`061:122`) but verify it is actually enforced in prod — the same audit notes RLS is dormant (no `FORCE`, pooled `set_config`) for `assets` (`docs/security/2026-05-30-...md:141`), so do not rely on RLS for DEK isolation; scope every `encryption_keys` query by `workspace_id` in Go.

#### Interaction with the public `thumbnails/*` bypass (explicit)
- The current direct anonymous bypass is a migration convenience, not the enterprise target. Retire it once the decrypt proxy and gallery-session/share-token model are in place.
- Do not decrypt for a totally anonymous caller. "Public" gallery media still needs a scoped authorization primitive: published gallery state, password/session or share-token validation when configured, expiry/access-count checks, and a short-lived media URL. This keeps public galleries usable without returning to direct B2/CDN plaintext object URLs.
- CDN strategy changes from "cache plaintext thumbnail objects forever" to "cache ciphertext or cache short-lived proxy responses carefully." That costs more engineering and some edge-cache efficiency, but it aligns with the strict upload/security contract.

### A.4 Performance budget

| Concern | SSE-C (Tier 0) | App-layer GCM (Tier 1) |
|---|---|---|
| Encrypt CPU | On B2 (server). ~0 app cost. | AES-NI ≈ 1–3 GB/s/core. A 1 MB `display_webp` ≈ 0.3–1 ms; a 40 MB original ≈ 15–40 ms. Negligible vs the existing `cwebp` subprocess + `imaging.Fit` Lanczos resize (`thumbnail_service.go:204`, hundreds of ms). |
| Decrypt CPU on serve | On B2. ~0 app cost. | Per authorized media GET. Same per-byte cost. Applies to originals and every derivative, including thumbnails, because the direct anonymous bypass is retired. |
| Memory | None added. | **Must stream** — current `io.ReadAll` (`:86,:116`) is O(object size) per request and the dominant risk; streaming AEAD bounds it to a chunk. |
| Ciphertext overhead | 0 (B2 stores ciphertext same logical size). | 12-byte nonce + 16-byte GCM tag per object (or per chunk in streaming mode). Update `assets.size_bytes` accounting / `workspace_storage` widget math accordingly. |
| Caching | `Cache-Control: private, max-age=3600` already set (`main.go:2375`). SSE-C decrypt is transparent, so cached bytes are plaintext — fine for auth'd clients. | Decrypt happens before the proxy writes the response; the response body is plaintext, so HTTP caching is unaffected. Do **not** cache *decrypted bytes server-side* keyed by storage key without a tenant check (would re-open IDOR). |
| Latency budget | +0 (B2 handles inline). SSE-C adds a small header-processing cost server-side only. | Target < 5 ms added p50 for `display_webp` with AES-NI + streaming. Acceptable within the existing proxy's `io.Copy` path. |

**Net:** SSE-C is effectively free at the app layer. App-layer GCM is cheap *if* streamed; the work to make it safe is the streaming rewrite, not the cipher.

### A.5 Phased backfill migration path (no downtime)

The repo already proves this pattern works: `cmd/encrypt-existing` performed a server-side copy-onto-self pass (505/505 → SSE-B2) on 2026-05-20, is idempotent via a `HeadObject` pre-check, classifies object state (`stateAtTarget` / `stateSourceSSEB2` / `stateSourcePlain` / `stateWrongSSECKey`, `:298-305`), and exits 2 (safe to re-run) on partial failure (`:289-291`).

**Phase 0 — storage SSE baseline, zero app downtime.**
1. Set `STORAGE_SSE_MODE=AES256` for managed B2 or complete SSE-C key escrow/rotation/restore drills before choosing `SSE-C`.
2. Run `encrypt-existing --dry-run` to count plaintext/SSE-B2/SSE-C objects (`:211-217`).
3. Run `encrypt-existing` to bring existing objects to the chosen SSE baseline. Re-runs skip `stateAtTarget`.
4. Only after the bucket is fully migrated, roll the API with the matching read-path SSE settings. Ordering matters for SSE-C: if cmd/api flips to SSE-C reads before objects are migrated, GETs on still-plaintext objects fail.
5. FATAL in production if the chosen SSE baseline is missing or invalid.

**Phase 1 — fix authorization before decrypt proxy.**
1. Close cross-tenant gallery/asset/storage IDORs and make public gallery access server-enforced.
2. Add regression tests that prove another workspace cannot download/decrypt originals, display WebP, thumbnails, ZIP exports, or edge variants.

**Phase 2 — light up app-layer streaming envelope for all media.**
1. Retire or rewrite `EncryptionService`: switch its KEK to `PLATFORM_SETTINGS_KEK`, make `EncryptFile`/`DecryptFile` streaming, add GCM AAD = workspace id + storage key + variant. Instantiate it in `main.go` and inject into upload finalize, `ThumbnailService`, `/storage/*`, edge delivery, authenticated/public download, and ZIP export.
2. Add an append-only migration extending `assets` and `asset_derivatives` with algorithm/version/nonce/key-reference metadata. Do not recreate the existing `encryption_keys` table from migration 044.
3. **New writes first:** encrypt originals and every derivative (`thumbnails/*` and `derivatives/*`) on upload/derivative generation; set encryption metadata per object. The proxy decrypts only after authorization, so mixed plaintext/encrypted rows can serve during migration behind a temporary compatibility gate.
4. **Lazy backfill of historical objects:** a worker (modeled on `encrypt-existing`) iterates unencrypted assets and derivatives, for each: `Get` (SSE transparent) → stream-encrypt → `Put` → set encryption metadata. Idempotent, resumable, throttled, and observable.
5. **Retire direct anonymous thumbnail serving:** replace the `thumbnails/*` bypass with short-lived gallery/share scoped decrypt URLs and update public viewer code accordingly.
6. **Rotation:** new key version for new writes; re-encrypt-on-access or a scheduled job moves old objects to the new DEK, updating key references.

**Rollback:** Tier 0 — flip `STORAGE_SSE_MODE` back and re-run the migrator to SSE-B2/plaintext (data still readable because the app holds the key). Tier 1 — because plaintext and encrypted rows coexist, disabling decrypt for a workspace only works after a reverse backfill; safer to leave Tier 1 forward-only per workspace and gate at enrollment.

### Download Policy & Bulk Export Requirements

Current evidence shows download behavior is not yet modeled as a coherent product/security contract:

- `PublicAssetDownload` streams the original object only and applies watermarking opportunistically for JPEG/PNG sources when gallery watermark config is enabled. It does not expose WebP as a public download format, does not let a photographer allow/deny watermarked vs clean copies per gallery/share, and cannot safely watermark RAW/HEIC/TIFF originals.
- The authenticated dashboard lightbox builds direct `/storage/*` URLs instead of routing through the download API, so it bypasses format negotiation, `Content-Disposition`, audit/accounting hooks, and the future decrypt-proxy policy.
- `download_jobs`/ZIP export exist, but the synchronous `DownloadZIP` path is high-risk at scale and the `variant` field is not validated. This makes bulk export a performance and contract weakness, not a production-grade delivery feature.
- The schema already hints at intent (`galleries.download_enabled`, `download_quality`), but the UI/repository surface only reliably exposes the boolean. The missing concept is a typed download policy, not another one-off menu item.

Target behavior for enterprise-grade galleries:

1. **Photographer-controlled policy, enforced server-side.** Each gallery, album/sub-gallery, and share link should resolve a typed policy such as:
   - `enabled`
   - `allowed_formats`: `original`, `webp`
   - `default_format`: usually `webp` for client delivery, `original` when the photographer explicitly chooses it
   - `watermark_mode`: `none`, `forced`, `optional`, or `both`
   - `allow_single`, `allow_multi_select`, `allow_album_download`, `allow_full_gallery_download`
   - `max_assets_per_zip`, `max_zip_bytes`, `expires_at`, `require_password_or_share_session`
   - filename/ZIP template and whether metadata/manifest files are included
2. **Single-photo download choices.** Public and authenticated download APIs should support `format=original|webp` and `watermark=auto|on|off`, but only return combinations permitted by the resolved policy. UI menus must be a reflection of policy, not the enforcement point.
3. **Multiple selected photos.** Public grid/lightbox should support selecting multiple photos and creating a ZIP for exactly those assets when `allow_multi_select=true`. Selection state must use asset IDs already authorized for that guest/share context; the backend must re-check each asset membership and permission before enqueueing the job.
4. **Bulk downloads.** Albums/sub-galleries and full galleries need background export jobs, not long-lived synchronous request streams. Return a job id, progress, partial-failure report, and short-lived download URL after authorization. The job should be resumable/idempotent and capped by policy/quota.
5. **Watermark semantics.** Watermarking cannot be client-requested protection. If `forced`, all public exports are watermarked regardless of query params. If `optional`/`both`, the photographer decides whether guests may choose clean vs watermarked copies. Studio owners may be allowed clean originals even when guests are forced to watermarked copies, but that bypass must be explicit, audited, and role-gated.
6. **Original vs WebP semantics.** In-app display remains WebP-first. Downloads should offer both WebP optimized and original when the photographer allows both. WebP downloads should use the generated `display_webp`/export-quality derivative or generate an export derivative if watermarking is required; original downloads should preserve original bytes unless a watermarked-public policy intentionally creates a protected export copy.
7. **ZIP contents and provenance.** Bulk ZIPs should preserve safe original filenames, disambiguate collisions, include a `manifest.json` or CSV with asset id, original filename, exported filename, format, watermark state, dimensions, checksum, and failures, and avoid path traversal through sanitized `Content-Disposition`/ZIP entry names.
8. **Audit, accounting, and rate limits.** Emit download events for every single, selected, album, and full-gallery export with actor type, gallery/share/session id, format, watermark state, asset count, bytes, and job id. Apply per-gallery/per-share rate limits and egress quotas to prevent download amplification.
9. **Security alignment.** All download APIs must run through the same public-gallery access context: published state, password/session, share-token/PIN/email, expiry/access-count, `download_enabled`, asset membership, object-level workspace ownership, decrypt-proxy authorization, and app-layer media decryption. No direct B2 URLs and no full access JWTs in query strings.
10. **Fallbacks and failures.** If a requested WebP derivative is missing, the backend should either generate it asynchronously and report pending, or return a clear per-asset failure in the job manifest. Do not silently fall back to original when the photographer selected WebP-only delivery.

Recommended API shape:

- `GET /api/v1/public/galleries/{slug}/assets/{assetId}/download?format=original|webp&watermark=auto|on|off` for public single-photo downloads.
- `POST /api/v1/public/galleries/{slug}/downloads` with `{ "asset_ids": [...], "scope": "selected|album|gallery", "album_id": "...", "format": "original|webp", "watermark": "auto|on|off", "idempotency_key": "..." }`.
- Authenticated equivalents under `/api/v1/galleries/{id}/downloads`, using JWT claims plus gallery workspace ownership.
- `GET /api/v1/.../downloads/{jobId}` for status/progress and `GET /api/v1/.../downloads/{jobId}/file` for the short-lived ZIP file once complete.

Implementation notes:

- Prefer a typed `download_policy` JSONB column or normalized columns over continuing to overload `download_quality`; if JSONB is chosen, validate it with Go structs and database `CHECK`s for object shape/version.
- Reuse the future app-layer decrypt stream inside ZIP generation; never read full originals into memory unless bounded by a small file-size cap.
- Generate watermarked WebP/export copies as derived artifacts with explicit storage keys and metadata, not ad hoc untracked temp objects.
- Make the export worker concurrency-limited, cancel-aware, and observable; large jobs should survive API restarts and expose progress.
- Add Playwright coverage for public password-gated single download, public selected-photo ZIP, album ZIP, full-gallery ZIP disabled/enabled states, and photographer policy changes using `tests/photos/` filenames with spaces and parentheses.

### Additional Recommendations

1. **Create a `docs/configuration/gallery-runtime.md` source of truth.** Include all required and optional env vars, platform-settings keys, workspace BYOS overrides, defaults, production fatal conditions, and migration/backfill ordering.
2. **Add a `config doctor` command.** It should validate storage driver/value pairs, B2 vars, SSE mode/key shape, `PLATFORM_SETTINGS_KEK`, JWT keys, `FRONTEND_URL`, rate-limit knobs, and whether production would start in a plaintext or unsupported mode.
